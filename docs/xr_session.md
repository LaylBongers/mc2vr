# OpenXR session (in the game's frame)

The carrier runs OpenXR inside the game, on DXVK's own Vulkan device and queue: the game is 32-bit D3D9, OpenXR has no D3D9 binding, and DXVK's D3D9 interop (`ID3D9VkInteropDevice`/`Texture`, `src/carrier/vr/dxvk_interop.hpp`) exposes the Vulkan objects behind the game's device and textures. Requires DXVK ([platforms.md](platforms.md)). OpenVR is not used anywhere. History (git): until 2026-11-10 a separate 64-bit host process presented through D3D11 shared textures (`src/host/`); then, briefly, an in-process session thread drove the game through two hand-offs.

Source (`src/carrier/vr/`): `xr_session.cpp` (setup, events, the frame calls, published views), `xr_present.cpp` (Vulkan copy into the swapchains), `xr_runtime.cpp` (runtime DLL, no loader), `eye_share.cpp` (the eye images, [eye_images.md](eye_images.md)). The frame itself: our `PgPrimitive_SubmitToGPU` (`src/carrier/reimpl/render/submit_to_gpu.cpp`, [reimpl.md](reimpl.md)).

## Runtime and setup

No OpenXR loader: `xr_runtime.cpp` negotiates with the runtime DLL directly (`xrNegotiateLoaderRuntimeInterface`) and resolves everything through its `xrGetInstanceProcAddr`. Under Wine that is Proton's 32-bit `wineopenxr.dll`; it needs the 32-bit runtime registered for 32-bit processes and the Wine VR registry published before DXVK creates its instance (both the launcher's, [openxr_proton.md](openxr_proton.md) items 2 and 4). On Windows: `XR_RUNTIME_JSON`, else the 32-bit `ActiveRuntime` registry value, and the manifest's `library_path` (never run).

The engine's first Present hands over the device (`init.cpp` `on_engine_running` → `xr_session::start`); the next stereo frame runs the setup on the render thread: the D3D9 device's interop → DXVK's instance, physical device, device, queue (family + index) → instance with `XR_KHR_vulkan_enable` → HMD system → Vulkan graphics requirements (required before the session; the instance/device extensions the runtime needs are logged, DXVK enables them under Proton) → session on DXVK's device + queue → LOCAL space → the recommended per-eye size (to `render_size` at the next update tick, [render_resolution.md](render_resolution.md)) → swapchain formats → the copy command pool. Any failure: `xr: no OpenXR session — VR off for this run`; the game runs with camera pass-through.

## Frame loop

The game's stereo frame carries the OpenXR frame, with its state passed along as values (`xr_session::Frame`); a small frame thread runs the calls that block or change the session:

```
render thread, PgPrimitive_SubmitToGPU:
  xr = xr_session::begin_frame()        take the frame the frame thread began → xrLocateViews
  rendered = eye_replay::begin_left_pass(xr)   the views both passes render with
  pass 1 (LEFT) · begin_right_pass(xr.show): LEFT captured · pass 2 (RIGHT)
  have = eye_replay::end_frame(xr.show, &pair)  RIGHT captured, pair flushed to DXVK
  xr_session::end_frame(xr, rendered, pair)     acquire → copy → release, hand the layer back
  … Present, the next scene build (during SteamVR's throttle)
frame thread:
  events, xrBegin/EndSession → xrWaitFrame → xrBeginFrame → offer the frame → wait for its layer → xrEndFrame (SteamVR throttles here)
```

- Why the split: SteamVR throttles inside `xrEndFrame`. With every call on the render thread (the "woven" version, 2026-11-10), that thread sat in the throttle and could only build the next scene after the wake, so the scene build (2–4.4 ms, variable) landed between the pose and the deadline: 4.8 ms fresher poses, but 1.9 ms of slack and 2–3% missed frames. The frame thread takes the throttle; the render thread Presents and builds the next scene meanwhile, as engines split a render thread from the thread that submits to the runtime. Begin and end of a frame stay on one thread; the render thread only locates views and acquires/releases swapchain images, which OpenXR allows from any thread.
- One frame in flight, and a frame exists only when the game renders one: no re-submits. The runtime sees the game's real cadence; while the game doesn't render (a long load), the begun frame stays open and SteamVR shows its own loading void. The render thread waits at most 100 ms for a begun frame (`frameWait`), then renders without the HMD that frame (`noFrame`).
- Hand-off: one CRITICAL_SECTION + CONDITION_VARIABLE (`g_hand`); each begun frame has a serial, and a layer handed back for another serial is ignored, so a late hand-back can't land on the next frame. A frame being acquired/copied/released (`presenting`) is never withdrawn. After one 100 ms timeout the render thread stops waiting until a frame is offered again, so a stuck runtime can't cap the game at 10 fps. Reviewed independently (2026-11-10): no deadlock, double end or mis-attributed frame.
- `xr.show` = the runtime shows this frame (`shouldRender` and VISIBLE/FOCUSED); only then are the eyes captured. Other frames of a running session end with no layers, which the runtime needs to move the session along.
- The layer is submitted with the views both passes rendered with (`view_rewrite::begin_frame`: this frame's, or the previous ones held through a tracking drop of up to 250 ms); in debug camera modes with this frame's own views if valid. No pair (the transition frame after a Reset) or no views: the frame ends with no layers. A layer `xrEndFrame` rejects is counted (`layerRejected`) and the frame ended without it.
- A frame the render thread took but never handed back (a pass aborted) is handed back empty at its next `begin_frame`. Over 100 consecutive frame-call failures end the session.
- `begin_frame` / `end_frame` run at full x87 precision: the render thread is at D3D9's single precision, which broke the runtime's own frame timing ([x87_precision.md](x87_precision.md)).
- Published views: each frame's `ViewState` (pose/FOV per eye as OpenXR half-angles in radians, tracked flag, pose id, display time/period, session state) under an SRW lock, for the update thread: the camera-table union pose ([camera.md](camera.md)) and `render_size`'s HMD-in-use test. Pacing takes the display time from the frame itself ([pacing.md](pacing.md)).
- Session state, polled on the frame thread (also while it waits for a layer): READY → `xrBeginSession`; STOPPING → `xrEndSession` once no frame is open (a frame the render thread hasn't taken is withdrawn; a taken one gets 200 ms to come back); EXITING / LOSS_PENDING / instance loss → one `WM_CLOSE` to the game window (the engine's quit path is VM-protected, `MC2_G_RENDER_HWND`), the frame thread ends, and the render thread tears the session down. Recenter (reference space change) needs nothing: the camera follows each frame's views.
- 10 s log: `submit: frames … shown hidden noFrame | no layer: noPair noPose copyFail layerRejected`, `submit: latency pose->display … endFrame->display … prediction depth`, `submit: calls avg/max ms` (frameWait (render), waitFrame, beginFrame, acquire, waitImage, copySubmit, release, endFrame, queueLockWait).

## Presentation

`xr_present.cpp`: one command buffer per copy (3, each with a fence), recorded on the render thread and submitted on DXVK's queue under `LockSubmissionQueue` (which first waits until DXVK has handed every queued submission to Vulkan).

- Source: the VkImages behind the eye images' D3D9 textures (`GetVulkanImageInfo`: handle + resting layout). GPU-side ordering, no CPU wait: the pair is flushed with `FlushRenderingCommands` right after the RIGHT capture ([eye_images.md](eye_images.md)), so DXVK's writes to it are in its submission queue; the queue lock drains that queue into Vulkan before our submit, which makes our copy later in the `VkQueue`'s submission order. A pipeline barrier's first scope covers every earlier-submitted command on the queue, so the copy's barrier (`ALL_COMMANDS` / `MEMORY_WRITE`) waits for those writes on the GPU and makes them visible. The closing barriers return the eye images to their resting layout, ordered before the next frame's writes. The runtime's own use of the swapchain images is ordered after the copy the same way (it gets DXVK's queue).
- `vkCmdCopyImage`, raw bytes. Swapchains are created at the eye images' own size (re-created when it changes), so the copy is 1:1 and the image rect is the full swapchain.
- Format: the sRGB sibling of the eye images' format (`B8G8R8A8_UNORM` → `B8G8R8A8_SRGB`, R8G8B8A8 likewise). The LDR finals are already sRGB-encoded; the copy hands those bytes over unchanged and the compositor decodes them, so no double gamma. Without a sibling the UNORM format itself (logged: gamma off); without either, nothing is shown.
- Swapchain images: `UNDEFINED` → transfer → `COLOR_ATTACHMENT_OPTIMAL` before release (the `XR_KHR_vulkan_enable` contract for color-attachment swapchains; usage `COLOR_ATTACHMENT | TRANSFER_DST`). Both eyes' swapchains exist or neither. An image is released only after a successful wait (timeouts are retried); one that can't be released gets its swapchains re-created.
- Runtime calls that may use the queue (create/begin/end session, swapchain create/destroy, acquire/release, begin/end frame) run under DXVK's queue lock; `xrWaitFrame`, `xrWaitSwapchainImage`, `xrLocateViews` and `xrPollEvent` don't. No D3D9 call is made while it is held (DXVK's rule), and the pair's flush happens before.
- Device Reset: `eye_share::on_reset` (before DXVK's Reset) waits for our copies' fences before the textures go (DXVK doesn't track our use of its images); it gives up only on device loss.

## Live results

2026-11-10, Index at 90 Hz, 2016×2240 per eye, msaa 4x, SteamVR/OpenXR 2.18.4 through 32-bit wineopenxr.

- Current design (frame thread): 899–901 frames per 10 s, all shown, `noFrame noPair noPose copyFail layerRejected` all 0. Steady scenes: every frame on time, pose → display 33.2 ms, sim step exactly 11.11 ms; heavy scenes: about one late frame per 10 s. `endFrame` (the throttle, frame thread) 6.2–7.2 ms; `frameWait (render)` ~1.9–2.6 ms, the render thread's slack after Present and the next scene build; flush ~0.8–1.0 ms. GPU and CPU budget: [pacing.md](pacing.md#frame-time-headroom).
- Setup: session VISIBLE ~2–4 s after the first Present. Swapchain formats offered (VkFormat) `43 50 109 106 97 64 …`; the eye images are `B8G8R8A8_UNORM` (44, resting layout `GENERAL`) → swapchains `B8G8R8A8_SRGB` (50), 3 images. Cosmetic: the Reset to the render size takes one last window-size pair first, so the swapchains are made at 2560×1440 and re-made at 2016×2240.
- SteamVR's timing model (consistent over every run and design): it throttles in `xrEndFrame` (`xrWaitFrame` ~0.02 ms), which returns at a fixed phase, 2 periods (22.2 ms) before the display; the frame's predicted display is 3 periods after that wake. It does not move the wake or deepen the prediction for a late app; after a late frame it shortens one prediction to catch up (the 1–2-period frames in the depth histogram). Submitting earlier only lengthens the wait inside `xrEndFrame`: removing the CPU wait for each pair's GPU work (A/B, ~3.5 ms earlier submits) changed no latency.
- Design evidence: sampling the pose after the scene build (all calls on the render thread) gave 28.4 ms pose → display but 2–3% late frames ([Frame loop](#frame-loop)); the frame-thread split restores the old timing. A load stall (~780 ms at the hand-over to gameplay) drops the session to SYNCHRONIZED for 0.5 s while no frames come (accepted; see OPEN). The resize to the render size waits for gameplay: the loading phase renders without Presenting, and `render_size` decides at Present.
- Vulkan validation (`MC2VR_VK_VALIDATION=1 ./launch.sh`, Khronos layer 1.4.363 with synchronization validation, uncapped; session-thread design, same copy): clean for our objects. None of the handles the carrier logs (`xr: present: handles`, `share: … VkImage`, `xr: swapchain … VkImage`) appears in any message; all 9,638 were DXVK's own (a per-frame 16×16 internal copy, one DXVK barrier). Match by image, pool or fence handle: Wine passes non-dispatchable handles through unchanged, but wraps command buffers and queues.
- Clock: wineopenxr's `xrConvertWin32PerformanceCounterToTimeKHR` returned ~0, while `predictedDisplayTime` is CLOCK_MONOTONIC ns (it matched the system uptime); Wine's QPC is CLOCK_MONOTONIC since boot, so the latency log uses it (`xr: latency clock:` picks whichever lands near a predicted display time). The render thread's x87 drops to 24-bit at device Resets ([x87_precision.md](x87_precision.md)).

## OPEN

- More headroom (later pose sampling, 120 Hz) needs render-thread time back first: [pacing.md](pacing.md#frame-time-headroom) ranks the levers (scene build concurrent with submission, single-pass stereo by draw doubling).
- Whether 3 periods is SteamVR's pipeline at all: compare a native Linux OpenXR app's (`hello_xr`) predicted display time.
- `xrEndFrame`'s throttle runs inside DXVK's queue lock (~6.5 ms per frame), now on the frame thread while the render thread Presents and builds the next scene. DXVK's submit thread can't submit meanwhile; if its queue fills, the render thread's Present waits on the throttle. The session-thread design held the lock the same way with no missed frames. The lock is the spec's external synchronization for the queue the runtime uses in `xrEndFrame`; dropping it would need proof that wineopenxr/SteamVR don't submit there.
- While the game doesn't render (a load stall), the begun frame stays open and SteamVR treats the app as hung (the session dropped to SYNCHRONIZED for 0.5 s at the load → gameplay stall). Alternative: end an unclaimed frame empty after a few display periods and begin the next (empty frames, no images re-submitted), so the session stays FOCUSED through stalls. Undecided.
- `xrWaitFrame` on the update thread (the engine-integration split OpenXR allows) would let the simulation step to each frame's exact display time; today pacing estimates it (exact in the logs, `step avg=11.11ms`). Needs the update→render frame pairing across the engine's one-frame offset.
- Game exit: no teardown runs on process exit (Alt-F4 or the in-game quit), so the session is never destroyed cleanly and the runtime sees the client vanish; the frame thread is killed wherever it is, possibly holding DXVK's queue lock. Exits have been fine in every run. A clean exit would need a hook on the process's way out that stops the frame thread, joins it and tears down.
- Windows: SteamVR's changelog lists 32-bit OpenXR as a cross-platform feature (since 2.17), so a 32-bit runtime should exist there. Unexercised: the carrier's manifest lookup for it (`XR_RUNTIME_JSON`, else the `ActiveRuntime` value a 32-bit process reads, `xr_runtime.cpp`) and where SteamVR registers it.
- A re-created D3D9 device (not seen so far) would leave the session on the old VkDevice: logged, nothing more is shown.
