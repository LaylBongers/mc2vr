# Frame pacing

## `vsync=off`

The engine Presents once per frame (pass 1's present-prev is skipped through its own `g_SuppressPresent`, [render_outputs.md](render_outputs.md)); with vsync on, the desktop refresh would cap the game. `vsync=off` forces `D3DPRESENT_INTERVAL_IMMEDIATE` in the CreateDevice params: attach-time InlineHook of the game's `Direct3DCreate9` IAT thunk (`0x00a4e892`, single caller `RenderSystem_Init` `0x0074c7a0`) + VmtHook on the returned `IDirect3D9` (`CreateDevice` slot 16); the device-level `Reset` hook re-patches on Reset. Done at the D3D boundary because the engine's own CreateDevice call site is VM-gated (`FUN_0074c9b0` → ptr `0x024cd09c`) and the carrier loads before the device exists ([carrier.md](carrier.md)). Default off = hook not installed.

## Lockstep with the OpenXR frame loop

The session thread runs the OpenXR app loop with the game as the renderer: `xrWaitFrame` → `xrBeginFrame` → locate + publish the views for that frame's `predictedDisplayTime` → wait for the pair rendered from them → submit it in the same `xrEndFrame` ([xr_session.md](xr_session.md)). One game frame per OpenXR frame, no re-submits: a game slower than the display makes frames late, and the runtime's own timing and throttling handle it. (Free-running and re-submitting the newest pair hid the game's real cadence and latency from the runtime.)

Carrier side, `src/carrier/vr/pacing.cpp`, while the session is VISIBLE/FOCUSED:

- **Gate on the render thread:** the pass-1 pose sample (`view_rewrite::set_pass_eye`) waits (on a condition variable) until the session thread has published views newer than the ones the last frame rendered with. The update thread is never held, so the next frame's update and render prep (~4 ms) overlap the session thread's end-of-frame and `xrWaitFrame`; only the two passes and the end-of-frame GPU sync sit between publish and pair.
- **Simulation step = display time:** at the `GameShell_FrameTick` entry hook (update thread, before the game's QPC sample) `g_FrameDeltaSec` is overwritten so the simulation advances one display period per frame (the runtime's `predictedDisplayPeriod`, published with the views — exact when SteamVR changes rate), and catches up when the last rendered display time shows the display got ahead (missed frames). The update usually runs a frame ahead of the render thread's pose sample ([render_threading.md](reverse_engineering/render_threading.md)), so "previous target + period" is the normal case (`floored` in the `pace:` line), not a fallback. The governor still applies its own processing to the fed value (mode 0: clamp to [0.1, 100] ms, × time scale, minimum 5 ms, zero when paused — no smoothing). The engine's own value is the FrameTick *body* time, not the frame interval, so any wait outside it desyncs the simulation clock from the display; its dt governor can also quantize to whole frames of a target rate with a strict `>` (plates on `0x01175048`, `0x004c1690`, `0x004f5720`) — in that mode the fed value is 0.25 ms short so the governor rounds to the true frame count. Time scale, pause and clamps still apply.

Both waits are bounded so neither side can hang the other: render gate 50 ms, the session thread's pair wait 100 ms (only while pairs arrived in the last 500 ms). Log lines: `pace:` (gate waits, fed dt vs `g_Dt`, governor mode/rate), `submit:` (fresh/late/stale, wait times).

The stereo replay pass skips `LtiRenderer_BeginSubmit`'s per-submit GPU drain (a condition at the drain check in our `LtiRenderer_BeginSubmit`, [reimpl.md](reimpl.md)), so the CPU queues the right eye while the GPU still draws the left; DXVK's own hazard tracking covers buffer reuse. `debug_keep_replay_drain=on` restores the drain.

Head-pose consistency of the rendered pair: [camera.md](camera.md).

## Half rate = double image on moving objects

Below the display rate SteamVR runs the game at half rate (60 on a 120 Hz panel) and flashes each frame twice; moving objects the eyes follow then show a back-and-forth double image (desktop monitors smear instead, so the mirror looks clean). Confirmed: at 20% render resolution and 80 Hz the game ran near full rate and the double image was gone. SteamVR motion smoothing is not available on Linux, so the fix is frame rate.

## Frame-time headroom

At full HMD render size (2016×2240 per eye) the game holds 90 Hz on the Index (since the in-process session, 899–901 frames per 10 s with none late; the host path had occasional single missed frames). The engine does not limit the frame rate (governor mode 0 `Variable`, no `Sleep(n)`/QPC spin, `debug_wait_census`); the time is the render worker plus the GPU — prep ~2.6 ms (= `RenderShell_BuildSceneRecords`, 2–4.4 ms per window, [reverse_engineering/scene_record_build.md](reverse_engineering/scene_record_build.md)) → pass 1 ~2 → pass 2 ~1.5 on the CPU, then ~4 ms of GPU work per pair, waited out by the session thread before its copy ([eye_images.md](eye_images.md)) — while the update thread waits for the render task ([render_threading.md](reverse_engineering/render_threading.md)). With the gate on the render thread, publish → pair is the two passes + the GPU tail; the render thread still has ~4 ms of slack per frame at 90 Hz. GPU (`debug_gpu_census`, 100% / 90 Hz): ~7.9 ms of work per 11.1 ms frame — main scene 3.6 (pass 1) + 2.5 (pass 2), post chains 0.36 per pass, shadow atlas + square targets ~0.4 per pass, carrier blits ~0.36 in total; ~7,400 draws per frame. The eye-independent offscreen passes in the replay cost only ~0.35 ms GPU + ~0.35 ms CPU, so skipping them is not worth it. 120 Hz at full size does not hold: publish → pair (~3.5 ms of passes + ~4.2 ms of GPU per pair) does not fit one 8.3 ms frame, and SteamVR alternates between 120 and its 60 Hz half rate. Reaching it needs less GPU time per pair or frame pipelining (render the next frame while the GPU finishes the current one — allowed by OpenXR, one frame more latency). Occlusion culling (per-eye since 2026-11-10) bought only ~0.4 ms of slack ([occluder_boxes.md](occluder_boxes.md)). Reading `debug_gpu_census`: pass 1's first segment includes the render-gate wait, so its CPU time is not submission cost. OPEN lead: pass 1's main scene takes ~1.1 ms more GPU time than pass 2's for the identical draws (3.94 vs 2.84 ms, 2026-11-10); either idle time counted inside pass 1's timestamps or real first-pass cost (uploads, cache misses).

A ~340 ms stall every 30 s was the carrier itself: periodic view-table hex dumps written from the game thread, through a logger that disk-synced every line (~5 ms each under Wine). The dumps are now opt-in (`debug_view_dumps=on`) and the logger no longer syncs per line. Logging from game threads stays expensive in bulk — keep per-frame paths log-free.

The game's camera motion blur (`Mercs2.ini MotionBlur`) smears moving objects in VR.
