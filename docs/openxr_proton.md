# OpenXR under Proton/Wine

The launcher handles item 2 and checks item 4 before starting the game (`src/launcher/vr_registry.c`, `xr_runtime.c`). The game's session itself: [xr_session.md](xr_session.md). `WINEDEBUG=warn+openxr` shows wineopenxr's side.

1. Must run through `proton run`: plain `wine` gives wined3d, which has no Vulkan interop (the carrier logs `xr: the D3D9 device has no ID3D9VkInteropDevice`).
2. wineopenxr negotiation fails (-6, runtime "lacks" every extension) unless `HKCU\Software\Wine\VR` exists, `wineopenxr_init_registry()` ran and DWORD `state`=1 (normally published by vrclient_x64 for an OpenVR app; state=2 fails). `wineopenxr_init_registry` publishes the runtime's Vulkan requirements there (instance/device extension lists, GPU vendor/product ids), which DXVK reads in any process when it creates its instance and device. It creates an OpenXR instance in the calling process, so the launcher (32-bit) needs SteamVR's 32-bit runtime registered (item 4); it doesn't touch the process environment. The launcher sets `state` itself, then snapshots and clears the four published values, calls the init, and checks they came back (restoring the snapshot if not), so it logs `published by this run` or a warning. Two misleading signals, both harmless: `wineopenxr_init_registry` returns TRUE even when it publishes nothing, and Wine skips writing a value whose data is unchanged without touching the key's modification time. Neither can tell "published identical values" from "published nothing", hence the clear-and-check. The console's `LoaderInstance::CreateInstance chained CreateInstance call failed` / `xrCreateInstance failed` is the init's first attempt: wineopenxr asks for OpenXR 1.1, SteamVR answers `XR_ERROR_API_VERSION_UNSUPPORTED` (-4), and wineopenxr retries with 1.0, which succeeds (`WINEDEBUG=warn+openxr` shows `get_extensions version 0x41 unsupported`).
3. "Stuck in SYNCHRONIZED" has been SteamVR itself crashed — restart it first.
4. **32-bit OpenXR (the game's session, [xr_session.md](xr_session.md)) needs runtime selection for 32-bit processes on both sides.**
   - Windows side: Proton registers only `wineopenxr64.json` in the prefix (`drive_c/openxr`). The carrier loads Proton's 32-bit `wineopenxr.dll` and negotiates with it directly (`xrNegotiateLoaderRuntimeInterface`), so it needs no manifest there.
   - Linux side: wineopenxr's i386 Unix part uses the native OpenXR loader, which looks for `openxr/1/active_runtime.i686.json`, then `active_runtime.json`, in `$XDG_CONFIG_HOME`, each `$XDG_CONFIG_DIRS` entry, then `/etc`; first hit wins. SteamVR on Linux can register only its 64-bit runtime there (`active_runtime.json` → `steamxr_linux64.json`) while shipping the 32-bit one next to it (`steamxr_linux32.json`, since SteamVR 2.17); a 32-bit process then fails with "wrong ELF class". Re-registering SteamVR as the default runtime doesn't add the 32-bit entry.
   - Fix: register the 32-bit runtime the way the loader expects, once per user: `ln -s <SteamVR>/steamxr_linux32.json ~/.config/openxr/1/active_runtime.i686.json`. 64-bit processes are unaffected (they look for `active_runtime.x86_64.json`, then the undecorated file). The launcher repeats the loader's search for a 32-bit process and logs `32-bit OpenXR runtime: ok`, or a warning with the exact command (`xr_runtime.c`). The launcher's Wine VR registry init (item 2) and the game's session need this.
   - Why not per process: Wine gives a child process its parent's Unix environment, not the environment block passed to `CreateProcess` (checked with a test program reading the child's `/proc/<pid>/environ`), so a Windows launcher can't hand only the game an `XR_RUNTIME_JSON`. A session-wide `XR_RUNTIME_JSON` would break any 64-bit OpenXR process in the session.
   - Not related to item 2: that one replaces what a Steam VR launch publishes.

Session: LOCAL space, per-eye swapchains at the eye images' size. Swapchain format choice and the sRGB copy: [xr_session.md](xr_session.md#presentation).
