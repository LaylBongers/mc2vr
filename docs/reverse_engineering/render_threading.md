# Render threading model (important, easy to get wrong)

- **Update and rendering run on different threads** (live thread IDs, carrier `debug_wait_census`): `GameShell_FrameTick` (update, `InGameShellState_FramePipeline`) on one thread; `PgPrimitive_SubmitToGPU`, both stereo passes, `LtiRenderer_BeginSubmit` and `Present` on another, which also runs the task system's `TaskWorker_RunLoop` — rendering is a task (`RenderTask_RenderFrame`, [frame_chain.md](frame_chain.md)) picked up by that worker. `RenderSystem_Init` asserts the device is *created* on the window thread; it is *used* from the render worker.
- The render worker idles in `TaskWorker_RunLoop` (`Sleep(0)`) whenever it has no task — in lockstep that is mostly while the update thread waits in the frame gate ([../pacing.md](../pacing.md)).
- The update thread waits on render tasks inside `FrameTick` (`Sleep(0)` loop at `0x00876939` in `FUN_0087681f`), but not on the current frame's: when nothing holds the update thread, `FrameTick` N+1 routinely starts before the render thread takes frame N's pose — update and render pipeline by one frame.
- The render "queue" (`g_RenderQueue` @ `0x00ff3618`, [view_table.md](view_table.md)) carries the frame from producer to consumer: producers publish packet elements during the frame pipeline; the packet processing behind thunk `0x0050c660` (protected, SecuROM-mutated native code — [securom_vm.md](securom_vm.md)), called right after `SubmitWorldPackets`, turns them into draw-records + command streams consumed by `RenderFrame`/`ExecuteStream` on the render worker.
- The priority-boosted thread created during boot (`0x008271b0` → `FUN_00827450`) looks like a render thread (event wait, frame counters, Sleep-based pacing) but is the **streaming-IO worker** (`ReadFile` on package files). Don't hook it for rendering.
